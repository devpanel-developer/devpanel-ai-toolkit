# Manual database and files import (Drupal)

How a person moves an existing Drupal site's database and public files from its old hosting into a DevPanel application. Everything happens in the application's **VS Code terminal** on DevPanel.

Data never goes into Git, into the toolkit, or into the Claude conversation. Claude prepares the application before this and verifies the site after it; the import itself is done by you.

## 0. Before you start

| Check | Command (VS Code terminal) | Expected |
|---|---|---|
| Application deployed | — | Claude reported the deployment; the site shows the Drupal installer or a database error (normal: no data yet) |
| Drush available | `drush status` | Drupal version, `Database : Connected` or empty `db-status` |
| Tools present | `command -v tar gzip rsync scp wget unzip` | Paths printed; ask your DevPanel admin to add missing ones to `.devpanel/custom_package_installer.sh` |
| Free space | `df -h "$WEB_ROOT/sites/default/files" /tmp` | At least **2 × files size + DB dump size** free. If not, ask Claude to raise the application `storage` first |
| Same Drupal major | `drush status --field=drupal-version` here and on the old host | Same major; the target may be newer (then `drush updb` runs in step 5) |

Paths used below:

```bash
export IMPORT_DIR=/tmp/dp-import          # working directory, outside the repository and outside the web root
export FILES_DIR="$WEB_ROOT/sites/default/files"
mkdir -p "$IMPORT_DIR" && chmod 700 "$IMPORT_DIR"
```

If `/tmp` is too small, use a directory under `$APP_ROOT` **only** if it is outside `$WEB_ROOT` and ignored by Git:

```bash
git -C "$APP_ROOT" check-ignore -q "$IMPORT_DIR" && echo ignored || echo "NOT IGNORED - do not use"
```

Never use `.devpanel/dumps/`: the DevPanel deploy script imports and deletes anything there on the next deployment.

## 1. Export on the old host

Run on the **old** server (SSH, or the hosting control panel's equivalent).

**Database** (tens of MB):

```bash
drush sql:dump --gzip --structure-tables-list='cache,cache_*,watchdog,sessions' --result-file=/tmp/site-db.sql
# produces /tmp/site-db.sql.gz; without Drush:
# mysqldump --single-transaction --no-tablespaces -u USER -p DBNAME | gzip > /tmp/site-db.sql.gz
```

Control panel only (phpMyAdmin): export as SQL, compression gzip.

**Files** (GBs): if you have SSH, skip the archive and use `rsync` in step 2. Otherwise:

```bash
tar -czf /tmp/site-files.tgz -C /path/to/web/sites/default/files \
  --exclude=./css --exclude=./js --exclude=./php --exclude=./styles .
```

`css`, `js`, `php` and `styles` are regenerated by Drupal; excluding `styles` often saves the most space.

Record checksums: `sha256sum /tmp/site-db.sql.gz /tmp/site-files.tgz`.

## 2. Bring the data into the application

In the DevPanel VS Code terminal. Pick the first option that works.

**A. SSH to the old host (recommended for files)** — server to server, resumable:

```bash
rsync -az --partial --info=progress2 \
  --exclude=/css --exclude=/js --exclude=/php --exclude=/styles \
  user@old-host:/path/to/web/sites/default/files/ "$FILES_DIR/"
scp user@old-host:/tmp/site-db.sql.gz "$IMPORT_DIR/"
```

**B. No SSH** — put the archive at a temporary URL on the old host (random file name, outside any listed directory) and download it:

```bash
wget -O "$IMPORT_DIR/site-files.tgz" 'https://old-host.example/RANDOM-NAME.tgz'
```

Delete the archive from the old host immediately after the download: until then anyone with the URL can fetch the site's files.

**C. Database dump on your computer** (tens of MB): drag it into `$IMPORT_DIR` in the VS Code Explorer. Do not upload multi-GB archives through the browser.

Long transfers: run them inside `tmux` (or `nohup ... &`) so closing the browser tab does not stop them; `rsync --partial` resumes where it stopped.

Credentials: use SSH keys or type passwords only at the prompt. Start any command containing a secret with a space so it stays out of shell history (`export HISTCONTROL=ignorespace`). Never paste credentials into Claude.

Verify what arrived:

```bash
sha256sum "$IMPORT_DIR"/*      # compare with step 1
```

## 3. Import the database

```bash
cd "$APP_ROOT"
drush sql:query 'SHOW TABLES' | wc -l          # 0 or 1 = empty
```

If the target database is **not** empty and you intend to replace it, back it up and drop it first:

```bash
drush sql:dump --gzip --result-file="$IMPORT_DIR/target-before-import.sql"
drush sql:drop -y
```

Import:

```bash
gunzip -c "$IMPORT_DIR/site-db.sql.gz" | drush sql:cli
```

Database credentials come from DevPanel (`.devpanel/settings.devpanel.php`); do not copy the old host's database settings.

## 4. Import the files

If you used option A, the files are already in place. Otherwise:

```bash
tar -xzf "$IMPORT_DIR/site-files.tgz" -C "$FILES_DIR"
```

Private files (only if the old site had a private file path): copy them to `$APP_ROOT/private` the same way.

Permissions:

```bash
sudo chown -R "${APACHE_RUN_USER:-www-data}:${APACHE_RUN_GROUP:-www-data}" "$FILES_DIR" "$APP_ROOT/private"
sudo chmod -R 2775 "$FILES_DIR" "$APP_ROOT/private"
```

## 5. Update and check

```bash
drush updb -y
drush cr
drush status --fields=drupal-version,db-status,bootstrap
drush watchdog:show --count=20 --severity=Error
```

Then tell Claude **"data imported"**. It runs the site check and reads the HTTP logs.

Development or staging copy? Remove personal data and consider not copying files at all:

```bash
drush sql:sanitize -y                          # resets user emails and passwords
# composer require drupal/stage_file_proxy     # serves missing files from production on demand (code change: commit on a branch)
```

## 6. Clean up

```bash
rm -rf "$IMPORT_DIR"
```

- Delete `site-db.sql.gz` / `site-files.tgz` on the old host and remove any temporary URL.
- Remove temporary SSH keys or accounts created for the transfer.

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| `Unknown collation: 'utf8mb4_0900_ai_ci'` | Dump from MySQL 8, target is MariaDB | `gunzip -c dump.sql.gz \| sed 's/utf8mb4_0900_ai_ci/utf8mb4_general_ci/g' \| drush sql:cli` |
| `MySQL server has gone away` / `max_allowed_packet` | Very large rows | Re-export with `--skip-extended-insert`, or ask the DevPanel admin about `max_allowed_packet` |
| `Table ... already exists` | Target not empty | Step 3: back up, `drush sql:drop -y`, import again |
| Site still shows the installer | Import failed or went to another database | `drush sql:query 'SHOW TABLES' \| head`; re-run step 3 and read its errors |
| Images missing, originals present | Image styles not yet generated | Normal; they are regenerated on first request. `drush cr` |
| HTTP 403 on files | Ownership/permissions | Step 4 permissions |
| `No space left on device` | Storage too small | Ask Claude to increase application `storage`; delete `$IMPORT_DIR` archives already extracted |
| All users logged out | Different `hash_salt` | Expected after migration |

## What not to do

- Put dumps or archives under `$WEB_ROOT` (they become downloadable) or anywhere Git tracks.
- Use `.devpanel/dumps/`.
- Paste credentials, dumps or signed URLs into the Claude conversation.
- Import production personal data into development environments without sanitizing.
